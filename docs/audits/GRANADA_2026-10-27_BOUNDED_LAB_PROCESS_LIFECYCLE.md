# Granada 2026-10-27 — bounded disposable VM subprocesses and independent 440 Hz source pipe recovery

## Audited baseline / real defect

The source-only native DSP and isolated Windows VM drivers already have independent 100%/150% source proofs, signed lab package checks, source binary fingerprints, PnP cleanup and original Windows-default render protection. However, the real `run_disposable_lab.ps1` called `& dotnet`, `& Devcon.exe` and `& pnputil` without individual timeouts. An executable stalled on an OS audio/driver API could consume the **whole Actions workflow timeout**, causing external job cancellation before the script's `finally` cleanup ran.

The separate `probe_independent_app_route.ps1` redirected both stdout and stderr for its owned bridge and source, but waited for child exit **before draining** their output streams. A sufficiently chatty process can block on a full OS pipe and never exit; similarly the bridge could fill stderr before emitting its readiness marker, preventing the separate app from starting. A pass/fail test based on timeout alone is not sufficient; pipe handling must be proven by actual synthetic subprocesses.

## Changes

1. Added `native/virtual-driver/LabProcessGuard.ps1`, a device-independent child-process owner that builds safe `ProcessStartInfo.ArgumentList` arguments (no concatenated shell command line), starts both redirected stdout/stderr readers concurrently, enforces local 1–60-second deadlines and a 64KiB standard evidence length cap, reports actual exit code and kills **only the owned process tree** on timeout/error. The guard deliberately never prints raw stdout/stderr, which might contain private endpoint names/paths. The caller decides what to redact and preserve in a fresh evidence folder.
2. Actual disposable VM runner now invokes **list-devices (15 seconds), each native virtual/physical tone (20 seconds), Devcon installation (45 seconds), and only-owned-device PnPUtil removal (30 seconds)** through this guard. Device removal still occurs inside the existing `finally`, with failure requiring a VM snapshot restore; the safeguards against changing the default Windows render role, exact owned PnP device and seven-binary integrity remain. A failed child deadline raises locally so workflow cancellation is no longer the first normal stop mechanism.
3. Independent separate-source proof starts draining the bridge's stderr **before** checking `EXTERNAL_SOURCE_READY`; after readiness it immediately starts draining the remaining bridge stdout **before** launching/waiting for the tone app. Source stdout and stderr drain concurrently from process start, with local 6-second source and 8/9-second bridge deadlines. Readiness log is bounded (128 lines/32KiB), and output is rejected if streams exceed caps. Existing exact numerical source/physical proof parser, no-source negative controls and fresh session IDs are unchanged.
4. New hardware-free real child-process regression `test_LabProcessGuard.ps1`: generates **70,000 bytes each** in stdout and stderr, verifies both drains complete, rejects excessive logs, ensures nonzero exit codes are preserved, tests independent readiness when stderr is full, starts a deliberately hung child and verifies its **owned process is killed** within the 1.2-second local deadline. Static checks bind those tests to actual VM install/cleanup/independent-source call sites. Native Windows CI runs it and parses both scripts. No audio device, driver install, signing key or elevated permissions required.

## Limitations / security
This prevents common redirected-pipe stalls and long unresponsive child processes from consuming the entire 25-minute GitHub Actions deadline. It cannot guarantee that Windows will finish *kernel PnP operations* immediately after Devcon has been terminated, that a malfunctioning hypervisor will honor process-kill requests or that a self-hosted runner cannot itself crash. VM snapshot restoration remains mandatory; a failed cleanup cannot be rebranded success. The fix is evidence about subprocess lifecycle only, **not proof of a signed installed driver or physical amplifier sound**.

The experiment does not change the Windows production Equalizer APO fallback, public installer, Windows device default, audio DSP filters or account behavior. No new release/version. Keep #46/#48 open for physical owner-approved VM and speaker/monitor checks.
